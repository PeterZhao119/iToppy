# iToppy 设计与前置验证计划

## 1. 当前结论

可以开始产品与系统设计，但不应直接进入完整实现或批量美术制作。

项目最关键的风险不在桌宠界面，而在以下三点：

1. 目标框架的落盘记录能否稳定识别“用户提交任务”和“整个任务的最终结果”。
2. macOS 悬浮窗能否在普通桌面、全屏应用、多 Space 和多显示器下保持预期行为。
3. 前端动画长期常驻时，能否保持低资源占用并正确响应拖动、点击和鼠标穿透。

因此采用“技术验证 → 设计冻结 → MVP 实现 → 扩展适配”的顺序。前置验证未通过时，先同步事实与限制，不用推测性状态掩盖问题。

## 2. 已确认的产品原则

- 平台优先为 macOS，角色使用前端技术渲染。
- 默认采用无感接入：只读监控磁盘记录，进程信息只作辅助；不修改框架源码、配置或注入插件。
- 不扫描全盘，只监控经过适配器登记的日志、会话和状态文件位置。
- 桌宠展示任务状态、最新响应和成功/失败情绪，并可点击跳转到来源 App。
- 成功和失败是持续结果，不在动画播放完毕后立即回到普通 idle。
- 首版优先支持明确验证过的框架，不承诺“所有框架均可精确识别”。
- 首版优先保证预设角色的质量；任意单图自动生成动作作为独立的高级能力验证。
- 监控数据默认仅在本机处理，不上传提示词、代码、日志或会话内容。

## 3. MVP 范围与非目标

### 3.1 MVP 范围

- 启动后按各适配器登记的默认路径自动发现 Agent，并支持用户按“Agent 类型 + 目标目录”手动添加。
- 提供控制面板，让用户选择展示并监控的实例、管理官方角色和调整设置。
- 每个活跃来源实例对应一只透明、无边框、置顶桌宠；IDE 按工作区、CLI 按终端会话区分，首版只启用 Kimi Code，详见 `design/source-instance-lifecycle.md`。
- 首个适配目标为 VS Code 中的 Kimi Code 插件，桌宠身份牌明确显示“Kimi Code”，不能降级成通用 VS Code 标识。
- 一套统一任务状态机和最新响应展示；running 支持思考、工具调用和搜索子动作，气泡展示当前活动短消息或公开正文前 50 字，只有任务级最终结果才结束 running。
- 成功/失败气泡显示前 50 字、最多四行，进入结果 `_idle` 后也不自动消失，直到用户关闭或新任务到来；点击气泡跳转来源 App，开关采用 App 默认值和来源实例覆写。
- idle 和结果 `_idle` 状态支持低速游走，游走开关和速度采用 App 默认值和来源实例覆写，并纳入当前实例的右键菜单。
- 新任务自动显示桌宠，结果降低提醒强度后不自动隐藏；只有手动“隐藏并暂停监控”才停用该实例。
- 角色可被鼠标拖动，右键提供精简上下文菜单。
- 2～3 个官方 Q 版人形角色，共用全身透明相位图和 Sprite Sheet 规格；首版不开放用户生成。
- 本地角色选择、音量/静音、置顶和启动设置。
- 适配器诊断信息，明确区分“没有任务”和“监控不可用”。
- 官方角色制作管线按独立流程设计和验证，详细交互见 `design/rough-design.md`。

### 3.2 暂不作为 MVP 阻塞项

- CLI 及其他 AI Coding 框架的适配。
- 任意单图自动生成稳定、高质量动作。
- 精确切换到每个终端标签页或每个 VS Code 内部视图。
- Windows、Linux 和移动端。
- 云同步、账号体系和远程监控。
- Live2D、骨骼动画或生成式动画的全面接入。

## 4. 总体设计方向

候选默认技术路线为 **Tauri 2 + 前端角色层 + 必要的 Swift/AppKit 原生辅助模块**。Tauri 2 已提供透明窗口、置顶和跨工作区配置，但是否需要原生 `NSPanel` 补足全屏、焦点和点击行为，必须通过原型决定，不能仅凭配置项冻结技术选型。

逻辑模块划分：

```text
框架专属只读适配器
  ├─ 文件变更监听与增量读取
  ├─ 版本专属记录解析
  └─ 来源会话与 App 定位信息
            ↓
统一事件模型（提交、最终成功、最终失败、中断、监控异常）
            ↓
每会话任务状态机 + 每来源实例聚合规则
            ↓
展示状态控制器（结果强弱、人物心情、响应气泡）
            ↓
每来源实例一只前端桌宠、动画、交互与本地设置
```

辅助模块：

- **进程与来源定位**：只辅助判断退出和激活 App，不用于臆测 Agent 内部状态。
- **本地持久化**：保存用户设置、各框架桌宠位置和必要的会话游标，避免重启后重复处理旧日志。
- **诊断与隐私**：保留可排错的本地状态，不默认复制完整敏感日志。

## 5. 需要完成的设计

### 5.1 产品交互设计

需要定义：

- 各任务状态下的人物、图标、动画和响应气泡表现。
- 单击、双击、拖动、悬停、右键和菜单栏入口，避免手势冲突。
- 最新响应的摘要长度、展开方式和隐私显示策略。
- 每个来源实例一只桌宠及其“Kimi Code · 工作区”身份牌；同一工作区内多个并发会话聚合到该桌宠，点击后可选择目标会话。
- 成功/失败结果持续多久后降低视觉强度，以及新任务如何打断旧结果。
- 监控不可用、日志权限不足和适配器版本不兼容时的界面表达。
- 多显示器、全屏应用、勿扰和静音场景下的行为。

### 5.2 状态机设计

任务状态与展示状态应分离：`_idle` 是降低提醒强度，不是抹掉任务结果。running 内部再记录当前活动子状态。

```text
idle ──用户提交任务──> running.generic

running ──明确思考输出──> running.thinking
running ──明确工具调用输出──> running.tool_calling
running ──明确搜索输出──> running.searching

running ──任务级最终成功──> succeeded
running ──任务级最终失败──> failed
running ──明确中断且无最终结果──> idle

succeeded ──经过设定时间──> succeeded_idle
failed    ──经过设定时间──> failed_idle

任何可接受新任务的状态 ──用户提交新任务──> running
```

设计约束：

- running 子动作只表示当前活动，不能作为任务最终结果。
- 没有新输出时保留最近子动作，不根据磁盘安静推断 idle。
- 只响应任务级最终结果，不把单次工具调用结果当作任务结果。
- 状态机按会话运行，通过会话/请求标识配对事件。
- 超时不自动等于失败；监控健康状态与任务状态分开处理。
- 成功/失败后保留最新响应，进入 `_idle` 后仍可查看。
- 应用重启时不能仅因历史记录存在未完成请求，就恢复为 running。
- 所有状态转换使用可重放记录测试，包括乱序、重复、缺失和并发事件。

### 5.3 适配器与统一事件设计

每个适配器需要声明：

- 支持的框架及版本范围。
- 监控路径、文件格式和日志轮转规则。
- 能精确识别、只能推断或完全不支持的状态和活动。
- 会话 ID、请求 ID、工作区、来源 App 和进程关联方式。
- 解析失败时的降级行为，不得伪报成功或失败。

统一事件至少覆盖：

```text
task_submitted
activity_observed(thinking|tool_calling|searching|generic)
task_succeeded
task_failed
task_interrupted
source_updated
monitor_degraded
```

文件监控采用事件驱动和增量读取。需要处理文件截断、轮转、缓冲写入、重复事件、大日志和读取游标持久化，不采用持续全文件轮询。

### 5.4 macOS 桌面窗口设计

需要验证并设计：

- 透明背景、无边框、阴影和透明区域点击穿透。
- 角色可拖动区域与按钮点击区域。
- 点击桌宠时不无意义地抢走来源 App 焦点。
- 普通窗口置顶、跨 Space、全屏 Space 和多显示器移动。
- 系统休眠唤醒、显示器拔插和分辨率变化后的位置恢复。
- 菜单栏图标、开机启动和退出方式。

“永远最前”定义为尽可能悬浮于普通应用和桌面 Space 之上，不承诺覆盖锁屏、系统权限弹窗等系统级界面。

### 5.5 来源 App 跳转设计

每个会话尽可能保存以下来源信息：

```text
framework / sessionId / pid / bundleId / workspacePath / terminalSession
```

跳转分级：

1. 激活来源 App。
2. 定位对应 VS Code 工作区或终端会话。
3. 精确终端标签页、VS Code 内部视图作为增强能力，需要额外权限或接口时单独确认。

### 5.6 角色与动画设计

首版使用官方角色的全身透明相位图和 Sprite Sheet，不使用 Live2D 或骨骼运行时。播放器优先验证 Canvas 2D，只有性能或功能证明有必要时才评估其他渲染框架。

需要形成统一规格：

- 完整角色帧的画布尺寸、透明边界、脚底锚点、缩放和高分屏策略。
- 帧率、循环方式、动作优先级和切换时的平滑规则。
- `idle / walk / running.generic / running.thinking / running.tool_calling / running.searching / succeeded / failed / succeeded_idle / failed_idle / dragging` 动作矩阵。
- 文件命名、图集打包、内存预算和素材许可证记录。
- 官方制作管线可使用图像工具及可选的关节/网格辅助，但最终必须人工验收并导出全身相位帧。

首版不提供用户生成或导入角色入口。后续若开放，需要另行验证输入范围、角色一致性、修正流程和成本。

音效和语音属于可选增强，默认克制且可静音，不阻塞核心监控链路。

### 5.7 开源、隐私与发布设计

- `.env`、其他本地密钥和 `skills/` 不进入公开仓库。
- 后续提供仅含变量名和占位符的 `.env.example`，不得复制真实值。
- 发布前执行 Git 忽略检查、历史扫描和素材许可证检查。
- 评估开发者签名与公证；本地进程/日志监控路线不优先以 Mac App Store 为发布前提。
- 文档明确读取哪些路径、为何读取，以及数据不会默认上传。

## 7. 分阶段实施顺序

### 阶段 A：技术验证

完成 P0-1～P0-6，保留真实调用记录、性能数据、限制清单和原型验收结果。

### 阶段 B：设计冻结

根据验证结果形成：

- 产品交互稿与状态视觉矩阵。
- 系统架构与统一事件协议。
- 状态机转换表和异常恢复规则。
- Kimi Code VS Code 插件适配器规格。
- 角色模板、动画规格和资源预算。
- MVP 验收清单。

### 阶段 C：MVP 实现

按“适配器 → 状态机 → 来源跳转 → 桌宠 UI → 设置与诊断 → 打包”的顺序集成。每一步使用真实任务链路验收，而不只验证模块能导入或能编译。

### 阶段 D：扩展

逐个增加 CLI 和其他框架适配器、预设角色、自定义素材导入和可选音效；任意单图生成动作按 P1-1 的结果单独排期。

## 8. MVP 端到端验收场景

至少完整跑通：

1. 桌宠明确显示“Kimi Code”身份牌，不被识别为通用 VS Code。
2. 用户提交任务，Kimi Code 桌宠进入 running。
3. 任务最终成功，展示成功图标、人物心情和最新响应；长时间后进入 succeeded_idle，结果仍可查看。
4. 任务最终失败，展示失败状态；长时间后进入 failed_idle。
5. 明确中断后回到 idle。
6. 等待确认、长时间无磁盘写入、日志轮转和进程退出不会产生虚假成功。
7. 点击桌宠激活 VS Code，并按能力定位工作区或目标会话。
8. 切换角色、拖动位置、切换 Space 和休眠唤醒后行为正常。
9. 新任务能打断旧的成功/失败展示并重新进入 running。
10. 日志不可读或格式不支持时，展示监控降级而不是伪造任务结果。
11. 整个过程中监控数据默认不离开本机，资源占用符合已记录的预算。
